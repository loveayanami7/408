## 文件
$$首先明确，文件本质上是一种抽象数据类型，包含逻辑结构、物理结构和文件操作$$
### 文件基本单位
1. 数据项
	1. 基本数据项
	2. 组合数据项
2. 记录：一组相关数据项的集合，描述一个对象在某一方面的完整属性
3. 文件：创建者定义、具有文件名的相关元素集合
	1. 有结构：若干格式相近的记录组成
	2. 无结构：连续字节流
### 文件系统结构（自底向上）
1. IO控制：
	1. 包含设备驱动程序和中断处理程序
	2. 设备驱动将高层指令转换为底层硬件可以识别的特定指令
	3. 硬件控制器执行
2. 基本文件系统：
	1. 负责向设备驱动程序发送通用命令
	2. 还管理内存缓冲区、缓存文件系统元数据、目录项及数据块
3. 文件组织模块
	1. 将文件的逻辑块地址转换为物理块地址（逻辑块顺序分配，物理块一般离散）
	2. 还包含空闲空间管理器，跟踪未分配的磁盘块
4. 逻辑文件系统（[[虚拟文件系统]]）
	1. 管理文件系统的**元数据**，不含实际数据内容
		* 元数据：描述文件系统结构的信息，如*文件名、目录项、权限和时间戳等*
	2. 维护目录结构，根据给定文件名向文件组织模块提供所需元数据
	3. 通过FCB（文件控制块）记录各文件的状态与属性
	4. 实现文件保护机制
### 文件逻辑结构
#### 无结构文件
1. 字节流组成
2. 通过读写指针定位字节（例如系统调用read/write(fd, buf, n)，fd作为文件名给出磁盘中起始地址，n为偏移量）
3. 只能顺序查找，效率低，不适合**频繁随机访问**或**按记录检索**
#### 有结构文件
1. 一个或多个记录组成，每条记录由若干数据项组成
2. 根据记录长度分：
	1. 定长记录：
		* 所有记录长度相同，数据项数量和长度不定，且数据项在记录中的位置固定
		* 可根据偏移量直接定位任意数据，从而支持高效的随机访问
		* 由于要为所有记录预留相同长度的空间，所以空间利用率不高
	2. 变长记录：
		* 记录长度不一，所含数据项数量不同/数据项长度可变
		* 无法直接算出记录位置，只能顺序查找，速度慢
		* 空间利用率高
3. 根据记录组织形式分：
	1. 顺序文件
		1. 记录按线性顺序依次排列，可采用定长或变长记录
		2. 按记录是否按键字排序分：
			1. 串结构：**记录按存入时间排序**，只能顺序扫描
			2. 顺序结构：**记录按键字有序排列**
				* 记录定长且键字有序：偏移量直接访问
				* 支持折半查找等高效算法
		3. 连续读取或写入大量记录时表现最佳（局部性强），对于顺序存储设备（磁带等）来说是唯一能有效工作的组织方式
		4. 频繁进行单条记录的操作性能不佳
	2. 索引文件
		1. 维护一张索引表记录文件中记录的索引号、长度和指针（起始地址）
		2. 将对文件的顺序扫描转化为对索引表的随机访问（偏移量，因为索引表项是定长的）
		3. 增加了存储开销
	3. 索引顺序文件
		1. 结合顺序和索引文件
		2. 先对变长记录顺序文件按关键字划分成若干组，组内记录无序，但组间有序
		3. 再为每组第一个记录建立索引表项，表项记录键字和指针（起始地址）
		4. 查询：首先根据键字**顺序访问索引表**确定属于哪个组，再在**组内顺序查询**
		5. 记录数量极大时还能通过**设置多级索引**降低查找开销
	4. 直接文件（散列文件）
		1. 关键字经过散列函数计算确定其物理地址
		2. 支持极快的随机存取
		3. 散列函数可能导致不同关键字映射到同一地址，引起冲突
### 文件物理结构
#### 什么决定文件的物理结构？
1. 文件的物理结构即文件数据在磁盘上如何分配与组织，所以磁盘块的分配方式决定了文件的物理结构
2. 磁盘块有空闲和非空闲，文件分配方式对应非空闲块管理，文件存储空间管理对应空闲块管理，这两种方式共同构成文件的物理结构
#### 文件分配方式（非空闲块管理）
1. 连续分配
2. 链接分配
3. 索引分配
#### 文件存储空间管理（空闲块管理）
1. 空闲表法FAT
	1. 相邻空闲块的合并
2. 空闲链表法
3. 位示图法
4. 成组链接法
	1. 索引块（组长块）
### 文件操作
#### 基本操作
1. 创建文件
	1. 合法性校验
	2. 从空闲inode池中分配索引节点，初始化元数据，标记已占用
	3. 从空闲磁盘块管理结构中分配相应数量的物理块，并将地址记录在inode中
	4. 在目录中创建新项，格式为<文件名，索引节点号>
	5. 更新文件系统元数据，包括空闲inode表、空闲磁盘块结构、目录大小以及修改时间等
	6. 打开并返回文件描述符(fd)[可选]
2. 删除文件
	1. 按路径名逐级查找目录，定位目标文件的目录项，获取其inode(通过索引节点号)
	2. 验证用户对目标文件的写权限
	3. 检查使用状态与硬链接计数：
		1. 硬链接计数>1：仅删除当前目录项，计数-1；
		2. 硬链接计数=1：进行以下完整删除流程
	4. 移除目录项，让文件在用户视角下消失（逻辑删除）
	5. 当链接计数降为0时，inode标记为空闲，归还至空闲管理结构，元数据彻底失效
	6. 根据inode中的块指针将物理块与索引块归还至空闲磁盘块管理结构
	7. 释放内存中对应的缓冲区、打开文件表项和内核文件对象等
	8. 更新文件系统元数据，包括目录大小、空闲inode表、空闲磁盘块结构等
3. 读文件
	1. 根据文件名在目录中查找对应目录项，获取索引节点号
	2. 定位数据块地址
	3. 根据当前读指针位置，从指定块中读取数据并更新读指针
4. 写文件
	1. 根据文件名在目录中查找对应目录项，获取索引节点号
	2. 定位数据块地址
	3. 根据当前写指针位置，写入数据：
		1. 空间足够：将数据写入目标块，更新写指针
		2. 空间不够：动态分配新磁盘块并更新inode中的块指针
#### 打开与关闭
##### 现代操作系统的两级打开文件表结构
* 系统打开文件表：
	* 全局共享，存储与进程无关的文件属性
		* 磁盘位置
		* 文件大小
		* 访问时间
		* ......
	* 每个表项包含一个打开计数器，记录当前有几个进程打开了该文件
* 进程打开文件表：
	* 进程独有，记录进程的私有访问状态
		* 当前读/写指针
		* 访问权限及文件打开模式
		* ......
	* 每一项均指向系统打开文件表中对应的表项
![[Pasted image 20260902170839.png|461]]
##### 打开文件
1. 用户调用open
2. 用户提供文件路径，系统逐级遍历目录，将所需的目录文件从磁盘加载到内存，定位目标文件的目录项
3. 从目录项提取其索引节点号
4. 比对系统打开文件表：
	* 若存在：对应表项的打开计数+1
	* 不存在：新建表项，打开计数初始化为1
5. 在发起请求的进程的进程打开文件表中添加新表项，记录其指向系统表项的索引
6. 将该表项的索引号作为文件描述符返回给用户进程，供后续读/写等操作使用
##### 关闭文件
1. 用户调用close
2. 系统从该进程打开文件表中删除对应表项
3. 系统打开文件表对应表项打开计数-1:
	* -1后仍>0：结束
	* -1后=0：该文件已无任何进程引用，删除系统表项，并释放相关资源（内存中的）
> [!note]
> 成功执行完`open()`系统调用，后续所有文件操作`read()`、`write()`、`lseek()`、`close()`等都不再使用文件名，而是通过文件描述符
### 文件共享
#### 硬链接
1. A、B用户的文件目录中都有指向同一索引节点的指针，该索引节点包含一个链接计数
2. 链接计数=0时才能真正释放该文件及其索引节点，链接计数>0时只能删除自己的目录项，链接计数-1
#### 软链接 
1. 系统创建一个类型为LINK的新文件L写入用户B的目录中，L中保存用户A的文件F的路径
2. 系统删除用户A的文件F，不影响用户B
### 文件保护
#### 文件访问控制列表ACL
* 为每个文件和目录附加一个访问控制列表
* 明确指定各用户名及其被允许的访问类型
* 用户一般被划分为：*拥有者、组、其他* 三种
* 用户访问文件时：
	1. 若为拥有者：授予拥有者权限
	2. 若与拥有者同属一组：授予组权限
	3. 否则授予其他权限
#### 其他保护机制
口令和加密，这两者均无法实现对访问类型的识别（是读？写？还是删除？执行？）

## 文件系统
### 虚拟文件系统
>[!important]
>VFS采用面向对象思想，抽象出一个通用的文件系统模型，并将其中的公共特性封装为四种对象，每个对象都包含数据成员和一组操作函数指针，这些函数由具体的文件系统实现，只要新的文件系统实现了VFS定义的接口，就能被系统识别、挂载并使用
#### 超级块对象 `struct super_block`

- **含义**：代表**一个已挂载的文件系统实例**（同一类型 fs 挂多处就有多个实例）。
- **来源**：磁盘型 fs 的内容从磁盘超级块读入；tmpfs/proc 等无磁盘实体。挂载时要先 `register_filesystem` 注册"文件系统类型"，挂载时再调该类型回调（fill_super）填充 super_block。
- **存什么**：块大小、文件系统魔数/类型、s_root（根目录 dentry）、s_op（分配 inode / 同步元数据等）。
- **对应关系**：1 super_block ⇄ 1 挂载实例。

#### 索引节点对象 `struct inode`

- **含义**：代表磁盘/内存中的**一个文件或目录**（对应磁盘 inode，是所有对象的"数据本体"）。
- **存什么（成员变量）**：权限、大小、时间戳、链接计数、指向 `address_space`（页缓存入口）。
- **操作（成员函数，注意分工）**：
    - `i_op`（inode_operations）：名字空间类操作 → lookup/create/mkdir/rename；
    - `i_fop`（file_operations 的来源）：在 open 时**拷给** file 对象，read/write 不直接挂在 inode 上调用；
    - `a_ops`：页缓存与磁盘的读写。
- **对应关系**：1 inode ⇄ 1 文件（内容主体）。

#### 目录项对象 `struct dentry`

- **含义**：**纯内存缓存**，不对应磁盘固定结构，是路径解析时动态生成的，把"路径名"映射到 inode。
- **存什么**：文件名、指向父/子 dentry、指向 inode 的指针。
- **关键关系**：**dentry 与 inode 是"多对一"**——硬链接使多个目录项指向同一个 inode。
- **作用**：缓存起来（dcache）加快后续路径查找；未命中的目录还有"负缓存"（记住"这里没有该名字"）。

#### 文件对象 `struct file`

- **含义**：一次 `open()` 的实例；进程私有的是 fd（fdtable 下标），file 是系统级、可被 fork/dup **共享**。
- **存什么**：当前读写位置 `f_pos`、访问模式 `f_mode`、引用计数 `f_count`、指向 inode/dentry 的指针、**函数操作表指针 `f_op`（→ file_operations，真正负责 read/write）**。
- **多对多**：1 inode 可被多个 file 打开；1 file 可被多个 fd/进程引用。
- **关系**：1 file ⇄ 1 次打开；file→f_op 在 open 时取自 inode→i_fop。
